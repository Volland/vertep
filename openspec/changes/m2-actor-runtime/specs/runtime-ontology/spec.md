## Purpose

Defines the `vt:` runtime ontology module: the RDF vocabulary for actors, addresses, mailboxes, journal entries, macrosteps, snapshots, timers, migrations and dead letters, with SHACL shapes as the validity contract and alignment to PROV-O that never requires a reasoner.

## ADDED Requirements

### Requirement: Runtime Vocabulary
The runtime ontology module SHALL define classes for actors (with subclasses for virtual actors, invoked actors and stateless workers), addresses, mailboxes, activations, journal entries, macrosteps, snapshots, timers, migrations and dead letters, and the properties linking them, in the `vt:` namespace and in a module separate from the chart module.

#### Scenario: Every runtime record is typed
- **WHEN** the runtime writes a journal entry, snapshot, timer, migration or dead letter to a graph store
- **THEN** each resource has an `rdf:type` from the runtime module

#### Scenario: Chart-only users need no runtime module
- **WHEN** a plain SCXML chart is projected to RDF without running it
- **THEN** the projection uses only the chart module and validates without the runtime module

### Requirement: Runtime SHACL Shapes
The runtime module SHALL ship SHACL shapes for each of its classes, and every journal entry the runtime writes SHALL conform to them.

#### Scenario: Written entries conform
- **WHEN** the shared test kit validates the RDF of journal entries written by any backend against the runtime shapes
- **THEN** validation reports conformance

#### Scenario: Malformed entry detected
- **WHEN** a journal entry without a message id or without a chart version is validated
- **THEN** SHACL validation reports a violation naming the missing property

### Requirement: PROV-O Alignment Without Dependency
The runtime module SHALL align with PROV-O by declaring macrosteps as subclasses of `prov:Activity`, input events and snapshots as subclasses of `prov:Entity`, and state statements as generated by macrosteps, and the runtime SHALL NOT need an RDFS or OWL reasoner for any of its own queries.

#### Scenario: Standard provenance query
- **WHEN** a user with an RDFS-aware store runs a PROV-O query for activities that used an input event
- **THEN** the macrostep that consumed that event is returned

#### Scenario: Runtime works without inference
- **WHEN** the runtime runs on a graph store with no inference
- **THEN** all of its own reads succeed, because they use only `vt:` terms

### Requirement: Triple Term Annotations
Annotations about runtime statements, such as which input caused a transition or the confidence of a choice, SHALL be written as RDF 1.2 triple-term annotations when the graph store supports them, and through the storage fallback otherwise.

#### Scenario: Annotating a transition taken
- **WHEN** a macrostep takes a transition and the graph store supports RDF 1.2
- **THEN** the statement that the transition was taken is annotated, through a reifier, with the journal entry that caused it

### Requirement: Stable Runtime IRIs
The IRIs of journal entries, snapshots, timers and dead letters SHALL be derived deterministically from the actor's address and journal position or send id, so that re-projection and replay produce the same IRIs.

#### Scenario: Re-projection yields the same IRIs
- **WHEN** the same journal is projected twice into empty graph stores
- **THEN** both stores contain the same IRIs for every runtime resource

### Requirement: Named Graph Layout
The runtime SHALL write each actor's current state into a named graph named by the actor's address, and each journal entry into a named graph named by the entry's IRI, so that queries can scope to one actor or one entry.

#### Scenario: Scope a query to one actor
- **WHEN** a SPARQL query uses `GRAPH <actor-address>`
- **THEN** it sees exactly that actor's current-state statements
