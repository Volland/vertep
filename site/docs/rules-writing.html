Writing rules

A rule program is a small ELPI program that reads the statements the shell wrote about one decision and concludes an event. This page is the reference for its shape, the names it can use, and the patterns that cover most policies.

The shape of a decision rule

A decision rule is a clause whose head is tm.conclude, a triple that names the decision and the event it concludes, and a list of the statements it rests on. The body is a sequence of lookups and comparisons.

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:approve")) [X, Eo, Ed, Ea] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X,
  tm.triple C (iri "urn:vt:offered") (iri "urn:vt:event:approve") Eo,
  tm.triple C (iri "urn:vt:ctx:dti") (num D) Ed, D =< 43,
  tm.triple C (iri "urn:vt:ctx:amount") (num A) Ea, A =< 50000.
  • tm.triple S P O E reads one statement: subject, predicate, object, and the variable that is bound to the statement's id. Bound arguments become index lookups, so a rule that starts from one decision node is cheap however large the shard is.
  • The list after the triple is the support: the ids the conclusion rests on. The host refuses a support that names a statement the run did not read.
  • Variables start with a capital letter. _ is a variable you do not need.

Terms

WrittenMeans
(iri "urn:vt:event:approve")An IRI.
(str "blocked")A plain string.
(num N)An integer; N is an ELPI int you can compare. Written with a variable it matches only integers.

The shell turns the fields of a decision's context into statements: an integral number becomes an integer, another number a double, a string a plain string, a boolean a boolean literal. Arrays, objects and absent values are skipped, so a rule can only read what is plainly data.

The vocabulary the shell provides

StatementMeaning
(urn:vt:ctx urn:vt:deciding C)The decision being made is the node C. Start every rule here.
(C urn:vt:offered urn:vt:event:NAME)The chart offered this event, written in offer order.
(C urn:vt:ctx:FIELD value)A plain field of the actor's context.
(C urn:vt:actor "…") and (C urn:vt:state "…")The actor's address and the decide state.
(C urn:vt:decision urn:vt:event:NAME)What a rule concludes.

The decision node is urn:vt:decision:<correlation>, one per offer. The context statement exists only for the length of one evaluation, so two decisions never see each other.

Why start from the context statement. tm.conclude runs over the whole view. A rule that does not start from one decision enumerates every decision in the shard: on a shard with 2 000 cases that took 118 ms against 0.27 ms for the same rule scoped by the context statement. The decider never calls the unscoped form.

How a conclusion becomes a decision

  • The decider takes the first offered event, in offer order, that the program concluded. Order your offer, not your clauses, when two events could both apply.
  • If nothing was concluded: refusal no-applicable-rule. If something was concluded but none of it was offered: not-offered. If the program concluded urn:vt:event:refuse and no offered event: explicit-refusal.
  • A run that exceeds the step budget is a refusal fuel-exhausted; the default budget is 1 000 000 steps, set in RulePolicy.

Patterns

Refer above a ceiling

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:refer")) [X, Eo, Ea] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X,
  tm.triple C (iri "urn:vt:offered") (iri "urn:vt:event:refer") Eo,
  tm.triple C (iri "urn:vt:ctx:amount") (num A) Ea, A > 50000.

Refuse on purpose

A catch-all that answers every case with refuse turns a silent gap into a recorded refusal, and is what the totality check looks for:

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:refuse")) [X] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X.

Share a limit between programs

A program can include another stored program. The closure digest of a decision covers the text of every included program.

accumulate <urn:vt:program:limits>.

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:approve")) [X, Ea] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X,
  tm.triple C (iri "urn:vt:ctx:amount") (num A) Ea,
  ceiling Max, A =< Max.

where urn:vt:program:limits holds pred ceiling o:int. and ceiling 50000.. The included program must be stored first. Note that a number written in an included program is not a statement, so it does not appear in the support; if you want the limit itself on the record, store it as a statement and read it with tm.triple.

An invariant on the journal

Constraints are written twice: a tm.violation-delta form that runs at commit, seeded by what the transaction added or retracted, and a tm.violation form that runs over everything, when enforcement is turned on. The two must say the same thing; a property test in the crate checks that they do for the example.

tm.violation-delta "blocked_actor" "the actor is blocked" [E1, E2] :-
  tm.added _ (iri "https://w3id.org/vertep/vt#actor") A E1,
  tm.triple A (iri "urn:vt:status") (str "blocked") E2.
tm.violation-delta "blocked_actor" "the actor is blocked" [E1, E2] :-
  tm.added A (iri "urn:vt:status") (str "blocked") E2,
  tm.triple _ (iri "https://w3id.org/vertep/vt#actor") A E1.
tm.violation error "blocked_actor" "the actor is blocked" [E1, E2] :-
  tm.triple _ (iri "https://w3id.org/vertep/vt#actor") A E1,
  tm.triple A (iri "urn:vt:status") (str "blocked") E2.

The second delta clause is easy to forget: a constraint can also be broken by adding the status to an actor that already has entries. Enforcement runs on every commit in the file, including the host's own writes, so this clause refuses that write too.

A derived fact with its cause

A tm.conclude whose conclusion is not a decision derives a fact. materialize writes it with its support:

tm.conclude (triple C (iri "urn:vt:risk") (iri "urn:vt:high")) [E1, E2] :-
  tm.triple C (iri "urn:vt:amount") (num A) E1, A > 50000,
  tm.triple C (iri "urn:vt:flag") (str "open") E2.

Stay inside the profile

Do not use: the cut (!), std.findall and other solution collectors, printing or reading, halting, time or random predicates, or any tm.* builtin other than tm.triple, tm.conclude, tm.violation, tm.violation-delta, tm.added, tm.retracted and tm.valid. Do not put negation inside a recursion. vt rules profile FILE reports every offending clause. A program outside the profile still runs, but its decisions are marked unchecked and no certificate is made for them.

Testing a rule

  1. vt rules profile program.elpi before you store it.
  2. Store it in a scratch shard with vt rules put and run vt rules check: it loads the program and runs it once under the step budget, so a syntax or type error shows up before anything decides.
  3. Run the example crate: cargo run -p vertep-rules --features native --example credit is a template for a decider, a bundle and a counterfactual in about a hundred lines (crates/vertep-rules/examples/credit.rs).
  4. Try the next version on recorded decisions with vt rules counterfactual, and run the totality check on your sample contexts. Checking rules has the details.
