Verification

The Rust code is fast and untrusted. A small Lean 4 model carries the proofs, runs as an oracle on the same inputs as Rust, and must produce the same traces. This page lists what is proven and how to run every check yourself.

Where the trust sits

The theorems are about the Lean model, not about the Rust code. The bridge between the two is trace equality: Rust runs a chart, records what it did, and the Lean step replays the same chart and inputs and must produce exactly the same configurations, effects and datamodel requests. Nothing is extracted from Lean into Rust.

  • A bug in Rust shows up as a trace difference or a failed W3C test, never as a wrong theorem.
  • A bug in the Lean model shows up as a failed proof, or as a trace difference that is then settled against the W3C text.
  • The proofs quantify over every datamodel answer, so they hold for every datamodel. They do not prove ECMAScript, CEL or any other expression engine correct.

The Lean package

The model lives in lean/vertep-lean, a Lake package pinned to leanprover/lean4:v4.35.0 (in lean-toolchain). It depends on LeanRDF, pinned to commit b407b97424150fec25a1ade514c71ea7abc61b42, for the RDF 1.2 data model and its SHACL Core validator. The library is compiled with warningAsError, so a sorry fails the build.

It contains the chart IR, a WellFormed predicate with a decision procedure proven correct, the executable step of W3C SCXML Appendix D, the RDF projection and its decoder, the type language, and three protocol models (journal, agent, lease). Next to the library, lakefile.lean builds seven executables:

vertep-oracleReplays a chart (as N-Quads) with Rust's recorded inputs and answer tape and writes or compares traces
vt-certifyThe checker behind vt certify
vertep-journalJudges observations of the Rust journal protocol against the journal model
vertep-decideJudges decision outcomes of the Rust agent machine against the agent model
vertep-leaseReplays cluster fault-injection histories against the lease model
vertep-typesChecks values against types, to compare with the Rust value checker
vertep-shapesRuns LeanRDF's SHACL validator with the chart shapes on N-Quads files, an empirical check of the shapes

The datamodel as an answer tape

Lean cannot run ECMAScript. So during a Rust run every datamodel request (evaluate this condition, assign this location) and its answer is written to a tape. In the oracle the Lean step must issue exactly the same requests in the same order, and it takes the answers from the tape. A request that differs is a trace difference. For the null datamodel, Lean evaluates In() itself and needs no tape.

What is proven

lean/vertep-lean/VertepTests/Axioms.lean pins the axioms of 78 main theorems. At build time it collects the axioms each one depends on and fails if anything other than propext, Classical.choice and Quot.sound appears. A sorry shows up as the axiom sorryAx, so it fails there too; the file even proves that the gate rejects a deliberate sorry. The main results, grouped:

The statement of the configuration theorem, from VertepLean/Config/Theorem.lean:

def ConfigurationWellFormedness : Prop :=
  ∀ c : Chart, WellFormed c → ∀ cc, compile c = .ok cc →
    ∀ s, Reachable cc s → s.terminated = false → Legal cc s.config

theorem configuration_wellformedness : ConfigurationWellFormedness :=
  configuration_wellformedness_of compile_cwf entry_legal

Proving it was not a formality. The attempt found three bugs in the W3C Appendix D entry algorithm as both cores implemented it, each producing an illegal configuration from a valid chart with history states. All three are fixed in Rust and Lean, with regression tests on both sides. The Rust property test crates/vertep-conformance/tests/config_legality.rs never generated those shapes, which is why the proof, not the test, found them. The protocol models found two more bugs in the Rust runtime (an outbox mark that passed refused sends, and colliding mailbox row IRIs when two nodes share a store), also fixed.

Some limits are deliberate. The type theorems read a pattern as the lexical rule its regular expression encodes; the regular expressions themselves are not proven equal to those rules. Lean decides int on the exact decimal while Rust decides it on an f64, so differential cases stay away from the edges of the signed 64-bit range.

Differential testing

Charts cross to Lean as N-Quads of their RDF projection, decoded by the same fromRDF that the round-trip theorem covers, so every differential run also exercises the projection. The Rust side records one JSON Lines record per macrostep: configuration, effects and datamodel requests. Sources of cases:

  • Generated charts. vertep-testkit generates well-formed charts and input sequences (crates/vertep-conformance/src/differential.rs). A disagreement is shrunk by proptest to a minimal chart and inputs and stored in crates/vertep-conformance/regressions/, which every run replays.
  • The IRP suite. Every runnable W3C test runs on Rust with its answer tape recorded; the oracle must give the same trace and verdict.
  • Validator against checker. Generated charts, and the same charts broken by one targeted mutation per validation rule, go to both the Rust validator and vt-certify (tests/certify.rs).
  • Protocols. tests/journal_protocol.rs drives two nodes sharing one journal store through crashes, redeliveries and concurrent activations and hands the observation to vertep-journal. tests/decide_differential.rs feeds adversarial decisions (stale and forged correlation ids, unknown or unoffered events, bad payloads) to the agent machine and has vertep-decide judge the outcomes. The cluster fault-injection test in crates/vertep-cluster/tests/faults.rs replays its history through vertep-lease.
  • Types. tests/types_differential.rs checks 4,000 generated declaration blocks, types and values with Rust and with vertep-types.

The full differential runs are #[ignore]d in normal test runs and need the Lean executables built. Small smoke samples run with the ordinary tests and skip with a message when the Lean build is missing. Two excerpts from a run of the full set:

The W3C IRP conformance suite

The W3C SCXML 1.0 Implementation Report Plan tests are committed under crates/vertep-conformance/suite/, copied from a pinned revision and transformed with pinned XSLT (confEcma.xsl, confCel.xsl); suite/SOURCE records where they came from and suite/SHA256SUMS pins the files, which the gate checks before it runs. Tests run in an in-memory host with several sessions, the SCXML Event I/O Processor and a virtual clock: no real time, no network.

The CEL datamodel runs the same suite through confCel.xsl variants of every datamodel-neutral template. Tests that have no CEL variant are listed with a reason in suite/cel/EXCLUDED.tsv.

The allow-list

Expected failures are listed in crates/vertep-conformance/allow-list.toml, each with the test, the datamodel and a reason. Three rules keep it honest: an allow-listed test that passes fails the run (so stale entries get removed), an entry without a reason is rejected, and an entry naming a test the suite does not have is rejected. Today it has 45 entries, all for optional ECMAScript tests:

EntriesReason
30The test uses the xpath datamodel, which Vertep does not implement.
12The test needs the Basic HTTP Event I/O Processor; the test host has no network.
2XML DOM values in the ECMAScript datamodel.
1Test 444 changes the datamodel inside a condition; Vertep evaluates conditions against a read-only scope by design (guard purity).

vt certify

vt certify asks the Lean model about one chart. It projects the chart to N-Quads and runs the Lean-compiled checker vt-certify on them. The checker decodes the graph with fromRDF, decides WellFormed, recomputes the version IRI from the canonical N-Quads and, if the chart is well-formed, prints a certificate as N-Triples. vt finds the checker through the VT_CERTIFY environment variable or as vt-certify on PATH.

cd lean/vertep-lean && lake build && export VT_CERTIFY=$PWD/.lake/build/bin/vt-certify

Its own IRI is a hash of its content, so certifying the same chart with the same checker gives the same certificate. vt certify prints the certificate; storing it next to the chart in a graph store is up to you.

You need the Rust toolchain from rust-toolchain.toml for everything, and elan (which installs the pinned Lean toolchain) for the Lean steps.

Under the differential feature a missing Lean build is an error rather than a skip, so build the Lean executables first.

What comes later

Proving the Rust code itself is deferred. The pure step kernel is kept in a style that Aeneas can translate to Lean (no async, no trait objects inside the kernel, no interior mutability, simple loops). When that work starts, a proof that the translated kernel refines the Lean step can replace the oracle for the kernel; the oracle stays for the shell, the datamodels and the stores.
