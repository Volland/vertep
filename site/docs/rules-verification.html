Checking rules

Five checks, from cheap and lexical to a Lean kernel. For each: what to run, what a pass means, and what it does not mean.

At a glance

CheckRun it withA pass meansIt does not mean
Profilevt rules profile FILEThe program uses only the part of the language whose meaning is order-independent and effect-free.That it is correct. The check is lexical.
Support necessityvt rules unnecessary BUNDLEEvery cited statement was needed for the conclusion.That nothing else mattered, such as constants in the program text.
Totalityvertep_rules::totalityNo offer in the sample falls through unanswered.Anything about contexts you did not sample.
Two enginestest oracleELPI and Datalog agree on a Horn join.Agreement on negation, or on the data both read.
Lean certificatevt rules certify BUNDLE --lean-dir DIRFor a clause of statement lookups and integer comparisons, the conclusion follows from the recorded statements.That the clause is the program's, or that the statements are in the store.

The rules profile

The profile is what the other checks are defined for. A program is outside it if it uses a cut, a solution collector (findall), printing or reading, halting, time or random predicates, an unknown tm.* builtin or a std. or io. builtin, or negates a predicate inside its own recursion. The check reads the text clause by clause: strings and comments are ignored, and the dependency graph is built from predicate names, so it flags exactly what it can see and accepts what it cannot.

$ vt rules profile cut.elpi
outside the profile: cut makes the meaning depend on the order of clauses [p X :- q X, !.]

The decider records, on each derivation, whether its whole program closure was inside the profile (profile_checked).

Support necessity

For each supporting statement of a bundle's decision, the check runs the rule in a fresh store with that one statement left out. A conclusion that still holds means the statement was not needed.

$ vt rules unnecessary bundle.json
every supporting statement is needed
# or:
support-not-necessary: e99999

Totality

use vertep_rules::{Totality, totality};

let events = ["approve", "refer"];
let contexts = vec![vec![("amount".to_owned(), Value::Number(10.0))],
                    vec![("amount".to_owned(), Value::Number(80_000.0))]];
match totality(POLICY, &events, &contexts, &RulePolicy::default())? {
    Totality::Total { checked } => println!("{checked} offers answered"),
    Totality::Gap { offer, context } => println!("nothing answers {offer:?} under {context:?}"),
    Totality::Unknown(why) => println!("not decided: {why}"),
}

The check runs the rule decider on every non-empty subset of the candidates (at most eight, so at most 255 offers) under each sample context, in a scratch store. A conclusion of refuse counts as an answer. It is a sampled check by design: it never claims anything about values you did not give it.

Two engines

The test crates/vertep-rules/tests/oracle.rs builds a random graph, asks tiramemsu's Datalog engine for grand(X, Z) :- parent(X, Y), parent(Y, Z), asks the ELPI engine for the same join, and requires equal answers. It is a regression guard on the engine, not a general equivalence proof.

The Lean certificate

The exporter finds the clause that derives the decision, matches its atoms against the bundle's statements to find a binding, and writes Lean source of this shape:

import VertepLean.RuleCert
open Vertep.RuleCert

def tape : List Fact := [
  { s := .iri "urn:vt:ctx", p := .iri "urn:vt:deciding", o := .iri "urn:vt:decision:c1", eid := "e5" },
  { s := .iri "urn:vt:decision:c1", p := .iri "urn:vt:ctx:amount", o := .int (20000), eid := "e4" } ]

def clause : Clause := {
  headS := .var "C", headP := .term (.iri "urn:vt:decision"), headO := .term (.iri "urn:vt:event:approve"),
  support := ["X", "Ea"],
  body := [ .triple (.term (.iri "urn:vt:ctx")) (.term (.iri "urn:vt:deciding")) (.var "C") "X",
            .triple (.var "C") (.term (.iri "urn:vt:ctx:amount")) (.num "A") "Ea",
            .cmp .le (.var "A") (.term (.int 50000)) ] }

def binding : Binding := [("C", .iri "urn:vt:decision:c1"), ("X", .str "e5"), ("Ea", .str "e4"), ("A", .int 20000)]

theorem cert : check tape clause binding (.iri "urn:vt:decision:c1") (.iri "urn:vt:decision")
    (.iri "urn:vt:event:approve") ["e5", "e4"] = true := by decide
#print axioms cert

check accepts an instance when every body atom holds under the binding against the tape, the head instantiates to the conclusion, and the support variables are bound to the recorded ids. check_sound and check_complete prove that this is the same as the instance being a derivation; triple_in_tape proves a statement id bound through a lookup really is on the tape. The axioms of all three are pinned in VertepTests.Axioms. The command runs the file with lake env lean as a process and refuses a theorem that depends on sorryAx or a native-code axiom.

cd lean/vertep-lean && lake build VertepLean        # once
vt rules certify bundle.json --lean-dir lean/vertep-lean
certified: urn:vt:decision:1001 ('cert' depends on axioms: [propext])
vt rules certify bundle.json --emit Cert.lean          # just write the source

What is trusted

  • The Rust parser that reads the clause out of the program text. Lean checks the instance it is given, not that it is the program's clause.
  • That each statement on the tape is in the store, which is the host's own check.
  • The engine version in the file: a certificate for a different engine version is not produced.

What is outside the fragment

Negation, other predicates, and arithmetic other than integer comparison. The exporter reports outside the certifiable fragment: … and never guesses. Widening it is possible (lean-elpi's own proof-term layer certifies Horn derivations over a fact tape) but needs tiramemsu to return the derivation tree, which it does not today.

The articles What a certificate proves, and what it does not and A reason that is not a story put these checks in context.
