Rules written by agents

A proposal goes through an ordered gate, is stored inert, can be run in shadow, and is promoted one stage at a time by someone who is not governed by it. This page lists the codes, the records and the commands.

The flow

  1. Propose. The text passes the gate and is stored as <program>/proposal/<digest>, in stage proposed, with its author, grant, source and scope.
  2. Shadow. Run it on recorded decisions beside the live program; differences are recorded; nothing is decided.
  3. Promote to shadow, then scoped (live for one named scope), then live. Each is a recorded act.

No decider reads a proposal and no enforcement runs it until the live step, which supersedes the live program with the proposal's text.

Gate errors

A refusal carries a stable code, the clause when there is one, and the reason. The first failing step stops the gate.

StepCodeRefused when
1self-governanceThe scope includes the proposer (or, at promotion, the promoter).
2capabilityThe host's capability check says the identity may not propose (or promote).
3type-errorA clause concludes an event the chart does not declare. The check finds event IRIs in the text; it does not type arguments.
4profileThe program is outside the rules profile.
5no-cases / trial-failedThere are no recorded cases and no waiver, or the trial run on them errors or runs out of steps.
6existing-dataThe program has constraints that the shard's data already violates.
promotionskipped-stepThe requested stage is not the next one; the reason names the one that is.
promotionstageThe proposal does not exist or is already live.

The agent tool

use vertep_rules::tools::{ProposeToolConfig, propose_tool};

let tool = propose_tool(ProposeToolConfig {
    shard, program: PROGRAM.into(),
    identity: "agent:a".into(), grant: "grant:propose".into(),   // fixed here, never an argument
    events: vec!["approve".into(), "refer".into()],
    cases: recorded_derivations, allow_no_cases: false,
    scope: vec![],                                              // actors the program would govern
    authorize: Arc::new(|who, action| /* the host's capability check */ true),
    policy: RulePolicy::default(),
})?;
// registered in the ToolRegistry as vt:tool/rules/propose

The tool takes { text: string, source: string } and returns { proposal: string }. A gate refusal is the tool's error text, a JSON object:

{"code": "type-error", "clause": "tm.conclude (triple C ...", "reason": "the chart declares no event `reject`"}

What is recorded

SubjectPredicates (urn:vt:rules:…)
the proposalforProgram, proposedBy, grant, source, scope (one per governed actor), stage, shadowDiffers (one per decision node where a shadow run differed), act
an act, <proposal>/act/<stage>actBy, actStage, actScope (for scoped), actDigest (the digest of the promoted program)

Read them with vertep_rules::authoring::{authorship, stage, act, shadow_differences}.

Scoped and live

A decider built with with_scope("team-a") runs the proposal that is scoped for team-a; a decider with another scope, or none, runs the live program. When the proposal goes live it supersedes the live program and the scope picks nothing out any more. The derivation of a decision from a scoped proposal names the proposal as its program, so its bundle verifies against the proposal's text.

The self-governance limit

Every proposal declares the actors it would govern (scope). If the proposing identity, or the identity promoting it, is one of them, the answer is self-governance, whatever grants it holds. A different identity that holds the promote grant and is not governed by the rule can promote it. The limit is structural: it does not depend on how the grants are configured.

Commands

# grants.json: {"propose": ["agent:a"], "promote": ["reviewer:r"]}
vt rules propose shard.db urn:vt:program:loan-policy next.elpi \
    --by agent:a --events approve,refer --cases derivations.json --grants grants.json
# proposed urn:vt:program:loan-policy/proposal/3f9a1c2b7d10

vt rules shadow  shard.db <proposal> derivations.json          # 0 unchanged, 1 differ
vt rules promote shard.db <proposal> --to shadow --by reviewer:r --grants grants.json
vt rules promote shard.db <proposal> --to scoped --scope team-a --by reviewer:r --grants grants.json
vt rules promote shard.db <proposal> --to live   --by reviewer:r --grants grants.json

--allow-no-cases waives the trial run when there are no recorded decisions, and --scope IRI,IRI on propose declares the governed actors. Skipping a stage is refused with skipped-step.

What the host provides

  • The capability check: a function from identity and action (propose, promote) to a yes or no. The command line reads a JSON file; wiring federation grant credentials into it is an integration for the host.
  • The recorded cases: the derivations of earlier decisions, for the trial run and for shadow evaluation.
  • The scope of each decider.
