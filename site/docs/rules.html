Rules

A policy that decides cases, written as a program and stored beside the journal it decides for. A decision made by a rule carries the statements it rests on, so it can be re-run offline, tried under the next version of the policy, and checked by the Lean kernel. This page covers the crate vertep-rules and vt rules.

This page is the overview. The reference is in four more pages: Writing rules (the shape of a rule, the vocabulary, patterns), Operating rules (storing, versioning, bundles, counterfactuals, enforcement, the commands), Checking rules (the profile, support necessity, totality, two engines, the Lean certificate) and Rules written by agents. Four articles give the reasoning: A reason that is not a story, The model proposes, the structure disposes, An agent that may not rewrite its own rules and What a certificate proves, and what it does not.

Why rules

The guard decider picks the first enabled candidate in document order, and a model's reason is its own claim. A rule's reason is a derivation: the statements about the case that made the conclusion follow. The engine is ELPI (a λProlog) run by lean-elpi through tiramemsu, which already stores programs as versioned nodes, so the rules and the journal live in one file and one transaction.

The native library is optional

Rules need the native library libleanelpi, which carries the Lean runtime. It is about 154 MB and exists for macOS and Linux on arm64 and x64, so it is behind a cargo feature that is off by default. Without it every constructor returns the typed error rules-unavailable and nothing falls back to another decider. The browser and Python packages do not contain it.

LEANELPI_DIST=/path/to/lean-elpi/dist cargo run -p vertep-rules --features native --example credit
cargo install vertep-cli --features rules   # vt rules ...

A rules decider

Before a rule runs, the shell writes the offer and the plain fields of the actor's context as statements in the shard, plus one statement naming the case being decided. Every rule starts from that statement, so a decision costs the size of the case and not of the shard. The rule concludes an event and lists the statements it used:

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:approve")) [X, Eo, Ed, Ea] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X,
  tm.triple C (iri "urn:vt:offered") (iri "urn:vt:event:approve") Eo,
  tm.triple C (iri "urn:vt:ctx:dti") (num D) Ed, D =< 43,
  tm.triple C (iri "urn:vt:ctx:amount") (num A) Ea, A =< 50000.

If no rule applies the decider refuses with no-applicable-rule; a program may also refuse on purpose by concluding refuse. Evaluation runs under a step budget, never a clock, and the record keeps the program closure's digest, the engine version and the fuel used. The credit example decides three loans, verifies a bundle with no shard, and tries the next policy on the recorded decisions:

deciding three applications by rule:
  1001  amount 20000, ratio 31%, offered ["approve", "decline", "refer"]
       derivation: approve from 4 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)
  1002  amount 80000, ratio 38%, offered ["decline", "refer"]
       derivation: refer from 3 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)
  1003  amount 45000, ratio 40%, offered ["approve", "refer"]
       derivation: approve from 4 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)

the bundle of the first decision, verified with no shard:
  2403 bytes; urn:vt:decision:1001 concluded approve from 4 statements: verified

the next policy (ceiling 30 000) tried on the recorded decisions:
  2 unchanged, 1 differ
  urn:vt:decision:1003: approve -> refer

Versions, bundles and counterfactuals

CallWhat it does
put_program, vt rules putStore or supersede a program; the earlier source stays readable as of its transaction.
verifyReplay a decision against the rules of its day and report a different engine version.
RuleBundle, vt rules bundle and verify-bundleExport a decision with its program closure and supporting statements and re-run it in a fresh store, no shard and no network.
counterfactual, vt rules counterfactualTry another program version on recorded decisions; nothing is written.
vt rules diffThe lines that changed between two versions of a program.

Invariants and derived facts

A program with tm.violation-delta and tm.violation clauses can be enforced: vt rules enforce checks the existing data first and is refused, with the violations listed, if live data violates it; after that a journal append that would violate it is refused at commit. The runtime writes no entry, acknowledges the message, records a dead letter that names the constraint and the statements, and the actor steps down unchanged. Enforcement runs on every commit in the file, including a host's own writes. materialize writes a program's conclusions as derived facts with their support, in the graph <subject>/derived; they fall when their support does and when the program stops concluding them.

Verification

  • Profile. vt rules profile says whether a program is inside the subset the checks are defined for (no cut, findall, input and output or clocks; negation stratified). Decisions from a program outside it are marked unchecked.
  • Support necessity. vt rules unnecessary removes each supporting statement in turn and reports one whose removal leaves the conclusion standing.
  • Totality. totality runs every non-empty subset of up to eight candidates under sample contexts and reports an offer nothing answers. It holds for those contexts only, and says unknown beyond the bound.
  • Two engines. A test runs a Horn program in ELPI and in tiramemsu's Datalog engine on a random graph and requires the same answers.
  • Lean certificate. vt rules certify BUNDLE --lean-dir lean/vertep-lean writes the decision's derivation as Lean source and the kernel checks that the conclusion follows from the supporting statements under the clause; the theorem depends only on propext. It covers clauses made of tm.triple atoms and integer comparisons; anything else is reported as outside the fragment. It does not check that the clause is the program's (the exporter's parser is trusted) or that the statements are in the store (the host's check).

Rules written by agents

An agent proposes a rule through the tool vt:tool/rules/propose or vt rules propose. The proposal passes, in order: the rule that an actor never proposes rules that govern itself, the capability check, the chart's event types, the profile, a trial run on recorded cases under fuel, and a check against existing data. The first failure comes back as a code, the clause and the reason, so the agent can repair it. A passing proposal is stored inert with its author, grant and source. Then vt rules shadow runs it beside the live program and records where it would differ, and vt rules promote moves it one stage at a time (shadow, scoped to a named scope, live), each step a journaled act by an identity holding the promote grant. An actor can neither propose nor promote rules that govern it.

What is not there

  • The derivation is not yet a field of the decision entry, and there is no whole-bundle vt verify-bundle; both belong to the decision-records work.
  • Erasing a data subject's key does not yet retract the derived facts that rest on their statements.
  • Grants for proposing and promoting come from a function the host supplies (a JSON file in the CLI); the federation layer's grant credentials are not wired in.
  • No rules in the browser, Python or Windows builds.
