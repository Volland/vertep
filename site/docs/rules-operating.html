Operating rules

Everything you do with a rule program once it is written: put it in a shard, bind it as a decider, read what it recorded, export a decision, try a new version, enforce an invariant. The commands are in one table at the end.

Setup

Rules run on the native library libleanelpi. It carries the Lean runtime, is about 154 MB, and exists for macOS and Linux on arm64 and x64, so everything that needs it is behind a cargo feature that is off by default.

# the library comes from a lean-elpi release (libleanelpi-<platform>.tar.gz)
export LEANELPI_DIST=/path/to/unpacked/dist
export DYLD_LIBRARY_PATH=$LEANELPI_DIST      # LD_LIBRARY_PATH on Linux

cargo test -p vertep-rules --features native
cargo install vertep-cli --features rules     # vt rules ...

Without the feature, constructors return the typed error rules-unavailable and nothing falls back to another decider. The repository's CI job rules downloads a checksum-pinned library for Linux and runs the vectors against it.

A rules decider

use std::sync::Arc;
use vertep_rules::{RuleDecider, RulePolicy, put_program};
use vertep_tiramemsu::TiramemsuShard;

let shard = Arc::new(TiramemsuShard::open("shard.db")?);
put_program(&shard, "urn:vt:program:loan-policy", POLICY)?;

let decider = Arc::new(RuleDecider::new(
    shard.clone(), "urn:vt:program:loan-policy", RulePolicy::default())?);
let host = AgentHost::builder(clock)
    .decider("underwriter", decider.clone())   // bound by name, like any decider
    .build();
// after the run:
let derivations = decider.derivations();       // the record of each decision

A Derivation holds the decision node, the event, the supporting statement ids, the digest of the program closure, the engine version, the step budget and the steps used, the transaction in which the offer was written, and whether the closure was inside the rules profile. The derivation is returned by the decider and is also carried on the journal's decision entry (as the annotation derivation, with no rationale text), so AgentHost::explain shows it as a derivation and not as an unverified claim.

Versions

A program is a node in the shard's file, edited by superseding its source statement. The earlier text is not lost: read it as of any transaction.

vt rules put   shard.db urn:vt:program:loan-policy next.elpi
vt rules show  shard.db urn:vt:program:loan-policy --as-of 12
vt rules diff  shard.db urn:vt:program:loan-policy --from 12 --to 40

A decision pins its closure by digest, the engine version and the fuel. verify replays a decision against the rules in force at its transaction and reports a different engine version, a changed closure, or a different conclusion or support, and a replay under a different engine version is refused with an engine-mismatch error.

Bundles

A bundle is one decision with everything needed to re-run it: the derivation, the program closure, and the supporting statements.

vt rules bundle shard.db derivations.json urn:vt:decision:1001 --out bundle.json
vt rules verify-bundle bundle.json     # no shard, no model, no network

Verification checks the engine version and the closure digest, loads the programs and statements into a fresh store, runs the rule, and compares the concluded event and the content of the support (statement ids differ between stores, so it compares triples). A bundle carries only the supporting statements, so offline re-running is sound for rules that read facts; a rule that depends on the absence of other statements may not conclude offline what it did live.

Counterfactuals

vt rules counterfactual shard.db derivations.json next.elpi
# 2 unchanged, 1 differ
# urn:vt:decision:1003: approve -> refer

Each recorded decision is replayed against the store as of its own transaction, with the offer in its recorded order, under the other program text. Nothing is written. A decision for which the other version concludes nothing is reported with the reason (no-applicable-rule, not-offered, fuel-exhausted).

Enforcement

vt rules enforce turns a stored program's constraints on. It first runs the full check over the shard's current data and is refused, with the violations listed, if live data already violates it. After that, a journal append that would add a violation is refused at commit:

  • the transaction aborts and nothing is written: the journal and its head are unchanged;
  • the store reports AppendError::Refused with the constraint name, its bindings and the offending statement ids;
  • the runtime acknowledges the message, records a dead letter whose reason is invariant: <constraint> (<statements>), and the actor steps down and reloads unchanged.
enforcing urn:vt:program:no-blocked-actor
actors/blocked is marked blocked
append for fine: committed, journal at 1
append for blocked: refused by blocked_actor (2 statements); journal still at 0

Enforcement is tiramemsu's, so it applies to every commit in the file, including a host's own writes, not only journal appends. Keep constraints about the journal narrow. vt rules unenforce turns it off.

Derived facts

vt rules materialize writes the conclusions of a program as facts, each with its support. They are members of the graph <subject>/derived, deliberately not the actor's state graph: the runtime compares the state graph with the machine's state after every turn and would read a derived fact there as a state change. A derived fact falls when any statement in its support is retracted, and when an edit to the program stops it concluding the fact. The report says whether the program may be non-monotonic (uses negation): such a program needs a re-run after writes. Retracting derived facts when a subject's key is destroyed is part of the decision-records work and is not built yet.

Scoped deciders

A decider bound to a scope runs the proposal promoted for that scope, and the live program otherwise:

let team_a = RuleDecider::new(shard.clone(), PROGRAM, policy)?.with_scope("team-a");

See Rules written by agents.

The vt rules commands

All need a build with the rules feature; without it they print rules-unavailable and exit 2. DB is the shard's tiramemsu file.

CommandWhat it does
put DB PROGRAM FILEStore or supersede a program.
show DB PROGRAM [--as-of TX]Print a program's source.
check DB PROGRAM [--fuel N]Load the program and run it once under a step budget.
diff DB PROGRAM --from TX --to TXLines that changed between two versions.
enforce / unenforce DB PROGRAMTurn commit-time enforcement on (checking existing data) or off.
materialize DB PROGRAM [--fuel N]Write the program's conclusions as derived facts.
bundle DB DERIVATIONS NODE [--out FILE]Export one decision's bundle.
verify-bundle FILERe-run a decision offline from its bundle.
counterfactual DB DERIVATIONS FILEWhere recorded decisions would differ under another program.
profile FILEWhether a program is inside the rules profile, and why not.
unnecessary BUNDLESupporting statements the conclusion does not need.
certify BUNDLE [--lean-dir DIR] [--emit FILE]The Lean certificate of a decision, checked by the kernel when a built vertep-lean is given.
propose, shadow, promoteAgent-proposed rules; see authoring.

DERIVATIONS is a JSON array of the derivations a decider recorded (serde_json::to_string(&decider.derivations())).
