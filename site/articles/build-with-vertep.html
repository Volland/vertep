A working guide

Build it as a chart

A refund desk in Vertep, step by step, and what XState, Akka and Orleans would ask of you instead

Some programs answer a request and forget it. Others live for days. An order waits for payment. A refund waits for someone to decide. A claim waits for a document, then for an assessor, then for a deadline. These long-lived programs fail in a particular way. Nobody can say afterwards exactly what happened, or why, or what the program would do now if you ran it again.

Vertep is built for the second kind. This article shows how to build one with it, from an empty file to a durable, replayable process with a language model or a person at its choice points. Every Vertep listing below is a file in the repository, and every output was pasted from a real run. Along the way the article asks what the same thing would take in three tools you may already use: XState, Akka and Microsoft Orleans. They are good tools, and at the end you will find a plain guide to when each is the better choice.

The idea in one picture

Vertep makes three decisions, and everything else follows from them.

  1. The program is a chart. Behaviour is a statechart: states, nested states, parallel regions, history, guarded transitions. A chart is data, not code. You write it in SCXML, the W3C notation, in YAML, or with a Rust macro. Each chart is named by the hash of its content, so a changed transition is a new version, and you can see which version did what.
  2. The actor is its journal. An actor is a running chart with an address. Every input it accepts is written to its journal before it is processed: messages, timer firings, and the answers of models and people. The state is whatever those inputs produce.
  3. The step is pure. The interpreter is one function, step(chart, session, input), with no I/O, no clock and no randomness. When the chart wants to send a message, start a timer or ask for a decision, step returns an effect, and a shell around it does the work. The result comes back later as another input, and goes into the journal like any other.

Some of what you get from that loop:

  • Restart. A process that stops loses nothing. The next one reads the journal and replays it through the same chart.
  • Time travel. The state at entry 17 is the replay of entries 1 to 17.
  • Replay without the world. A model's answer is a journal entry, so replay needs no model, no network and no person.
  • One history. An append succeeds only if the journal is still at the position the actor last saw. Two activations of one actor can never both extend its history.
  • Many hosts. The core runs natively, in WebAssembly in a browser or Node.js, and from Python. The same chart behaves the same in all of them.

What we will build

The example is a refund desk. A customer asks for a refund of some amount. A reviewer can approve it, reject it, or escalate it to a manager. There is one policy the business will not bend: a reviewer may approve at most 100 on their own, and anything above that goes to the manager. Who is the reviewer? Today it is a language model. Tomorrow it may be a person, or a rule program. The chart should not care.

Step 1. Install

The crates are on crates.io, the JavaScript packages on npm and the Python package on PyPI. A Rust program depends on the facade crate vertep. The vt command validates, hashes, converts and type-checks charts.

[dependencies]
vertep = "0.1"
cargo install vertep-cli          # the vt command
npm install @vertep/web@next      # browsers and Node.js
pip install vertep                # Python 3.9 or later

To follow along with the examples, clone the repository. Each example is a binary of the vertep-examples package, and cargo test -p vertep-examples checks that each one still prints what this page shows.

Step 2. Write the chart

Here is the refund desk as SCXML, from examples/decider-agent/refund.scxml. It uses the CEL datamodel: ctx is the actor's data and ev.data is the event's payload. Two attributes from the Vertep namespace make review and manager into decide states. vt:decide="policy" names the binding that will decide, and vt:candidates lists the events it may choose from.

<scxml xmlns="http://www.w3.org/2005/07/scxml" xmlns:vt="https://w3id.org/vertep/vt#"
       version="1.0" datamodel="cel" name="refund-agent" initial="idle">
  <datamodel>
    <data id="amount" expr="0"/>
  </datamodel>

  <state id="idle">
    <transition event="request" target="review">
      <assign location="amount" expr="ev.data.amount"/>
    </transition>
  </state>

  <state id="review" vt:decide="policy" vt:candidates="approve reject escalate">
    <transition event="approve" cond="ctx.amount &lt;= 100" target="approved"/>
    <transition event="reject" target="rejected"/>
    <transition event="escalate" cond="ctx.amount > 100" target="manager"/>
  </state>

  <state id="manager" vt:decide="policy" vt:candidates="approve reject">
    <transition event="approve" target="approved"/>
    <transition event="reject" target="rejected"/>
  </state>

  <state id="approved"/>
  <state id="rejected"/>
</scxml>

Read the guards. Above 100, approve in review is disabled, so it is never offered. Whatever decides here cannot approve a large refund alone, because the chart never presents that move. That is the most important property of the design, and we will come back to it.

Now ask vt whether the chart is well formed, and what its name is.

$ vt validate examples/decider-agent/refund.scxml
examples/decider-agent/refund.scxml: ok: urn:vertep:chart:sha256:c6282b762c855df3792c2fea39fc345df6ed5e317484461e5d0a7f8d68f292aa

That IRI is the chart's version. Change a guard and you get a new one. Every journal entry records the version it ran under, and an actor stays on its version until it ends or you migrate it explicitly, with a compatibility check. The same chart in YAML hashes to the same IRI, because the hash is taken over the chart's meaning, not its spelling:

$ vt convert --to yaml examples/decider-agent/refund.scxml

  amount:
    init: "0"
initial: idle

              location: amount

Step 3. Make it durable

Before we add judgement, look at the durable part on its own. examples/durable-actor runs an order with a payment window: after checkout the chart waits 15 minutes for pay, then expires. The timer is an ordinary <send> with a delay:

<state id="awaiting_payment">
  <onentry><send id="payment-timer" event="payment.timeout" delay="900s"/></onentry>
  <transition event="pay" target="paid"><cancel sendid="payment-timer"/></transition>
  <transition event="payment.timeout" target="expired"/>
</state>

The host opens a tiramemsu store (an SQLite-backed graph store), registers the chart under a type IRI, and sends messages to a virtual actor. There is no create call. The address type/key exists for every key, and the first message activates it. The idea comes from Orleans.

fn node(backend: Arc<TiramemsuBackend>, shell: Shell) -> Result<Node, Error> {
    let mut node = Node::builder(backend, shell)
        .datamodels(Arc::new(vertep_dm_cel::CelRegistry))
        .build();
    // `read_str` accepts only the `null` datamodel; name the ones the host supports.
    let opts = vertep::scxml::ReadOptions::new().with_datamodels(&vertep::scxml::AnyDatamodel);
    let chart = vertep::scxml::read(ORDER, &opts)?.chart;
    // Registering is idempotent: the same chart gets the same content-addressed version.
    node.register_type(ORDER_TYPE, chart)?;
    Ok(node)
let backend = Arc::new(TiramemsuBackend::open(dir, 1)?);
let mut node = node(backend, shell.clone())?;

// A virtual actor needs no create call: the first message activates it.
for name in ["add", "add", "checkout"] {
    node.send(&order, Event::named(name, EventType::External))?;
}
node.run_until_idle();

The example then drops the node and the store, as if the process had stopped. A second "process" opens the same directory ten minutes later on a virtual clock. Asking for the actor's state replays its journal. Five minutes after that, the timer the first process scheduled fires in the second one:

actor https://example.org/charts/order/42
process 1: ["awaiting_payment"] context={"items":2}
  entry 1 at +0s: add              timers scheduled: []
  entry 2 at +0s: add              timers scheduled: []
  entry 3 at +0s: checkout         timers scheduled: ["payment.timeout"]
  pending timer payment.timeout due at +900s
process 1 stops
process 2: ["awaiting_payment"] context={"items":2} (replayed 3 entries)
process 2 at +900s: ["expired"] context={"items":2}
  entry 1 at +0s: add              timers scheduled: []
  entry 2 at +0s: add              timers scheduled: []
  entry 3 at +0s: checkout         timers scheduled: ["payment.timeout"]
  entry 4 at +900s: payment.timeout  timers scheduled: []
as of entry 1: ["cart"] context={"items":1}

Three things to notice. The checkout entry carries the timer it scheduled, so the timer is part of the record and not a setTimeout in some process's memory. The firing is entry 4, an input like any other. And as of entry 1 rebuilds the past from the journal. Nothing had to be stored for it.

Tests run on a virtual clock (Shell::virtual_time) and drive the node with run_until_idle, so a fifteen-minute timeout takes no time and prints the same thing on every run. A server uses Shell::tokio() and node.run().await instead.

Step 4. Put judgement at the choice points

Now the refund desk. An agent host runs charts with decide states. A decider is bound to each binding name. When an actor enters a decide state, the host builds an offer, a DecisionRequest, holding the state, the candidate events that are enabled right now, a read-only view of the context, and a correlation id. The decider answers with one event, or refuses. The answer is journaled, then processed.

The example binds policy to a scripted decider, a stand-in for a model that answers from a list, so it needs no network and prints the same thing on every run. The host is built like this (examples/decider-agent/main.rs):

let mut host = AgentHost::builder(Arc::new(VirtualClock::new(T0)))
    .journal(journal.clone())
    .decider("policy", Arc::new(decider))
    .build();
let version = host.register(chart()?)?;
host.spawn(AGENT, &version)?;
host.send(AGENT, request(250));
host.run_until_idle();

A refund of 250 arrives. Here is the whole run, followed by a second host that opens the same journal with no decider bound at all:

run 1, decider bound to `policy`:
  decider asked in `review`: offered ["reject", "escalate"] -> escalate
  decider asked in `manager`: offered ["approve", "reject"] -> approve
  final: ["approved"] context={"amount":250}
journal:
  1 start
  2 event     request
  3 decision  escalate (offer https://example.org/agents/refund/7/decision/2.0, rationale "amount is above my approval limit")
  4 decision  approve (offer https://example.org/agents/refund/7/decision/3.0, rationale "manager approved: item returned unopened")
run 2, same journal, no decider bound:
  final: ["approved"] context={"amount":250}
  as of entry 2: ["review"]
  as of entry 3: ["manager"]
  as of entry 4: ["approved"]
  entries replayed: 4, decider calls: 0

The first line is the policy at work. In review, with 250, the decider was offered reject and escalate. approve was never on the table. Each answer is a journal entry with the offer it answered and the reason given, written before the chart acted on it. The replay then reaches the same final state and context with zero decider calls.

To use a real model, bind a LlmDecider instead. It asks for structured output whose schema is a choice over the offered candidates, so a model cannot name an event that was not offered. This binding is from crates/vertep-agent/examples/support/kit.rs:

let mut b = AgentHost::builder(Arc::new(clock.clone()))
    .provider("triage", Arc::new(triage))
    .decider(
        "llm/claude",
        Arc::new(
            LlmDecider::new("claude", Arc::new(model), "claude-opus-5-5").with_instructions(
                "You are a support agent. Use the tools, then finish with an answer.",
            ),
        ),
    )
    .decider(
        "human/support",
        Arc::new(GuardDecider::with_rules(vec![
            vertep_agent::decider::GuardRule {
                event: "finish".into(),
                guard: None,
                payload: Some("{'text': 'A person will get back to you.'}".into()),
            },
        ])),
    );

The other built-in deciders follow the same contract. A HumanDecider puts the offer in an inbox for a person. A GuardDecider picks by CEL rules. An ActorDecider asks another actor. A RuleDecider runs a rule program and records the derivation as its reason. Swapping one for another changes no line of the chart.

The same desk in XState

XState is the statechart library most JavaScript developers know, and it is excellent. Version 5 models statecharts with nested and parallel states, history, guards and delayed transitions, and treats invoked promises, callbacks and other machines as actors. Stately's visual editor works on the same machines. Here is the refund desk, written for this comparison. The model call becomes an invoked promise:

import { setup, assign, fromPromise, createActor } from "xstate";

const refund = setup({
  types: {
    context: {} as { amount: number },
    events: {} as { type: "request"; amount: number },
  },
  actors: {
    // your code: an LLM call, a queue for a person, a rules service
    policy: fromPromise<string, { amount: number; options: string[] }>(
      async ({ input }) => askModel(input),
    ),
  },
}).createMachine({
  id: "refund",
  context: { amount: 0 },
  initial: "idle",
  states: {
    idle: {
      on: { request: { target: "review", actions: assign({ amount: ({ event }) => event.amount }) } },
    },
    review: {
      invoke: {
        src: "policy",
        // the offer is computed by hand, and must agree with the guards below
        input: ({ context }) => ({
          amount: context.amount,
          options: context.amount <= 100 ? ["approve", "reject"] : ["reject", "escalate"],
        }),
        onDone: [
          { guard: ({ context, event }) => event.output === "approve" && context.amount <= 100, target: "approved" },
          { guard: ({ context, event }) => event.output === "escalate" && context.amount > 100, target: "manager" },
          { target: "rejected" },
        ],
      },
    },
    manager: { /* the same shape again */ },
    approved: { type: "final" },
    rejected: { type: "final" },
  },
});

const actor = createActor(refund).start();
actor.send({ type: "request", amount: 250 });
// to survive a restart, store a snapshot and restore from it:
await db.save("refund/7", actor.getPersistedSnapshot());

It reads well, and for user-interface logic it is hard to beat. The differences show when the process outlives the page or the server:

  • A snapshot, not a history. getPersistedSnapshot tells you where the actor is now. It does not tell you how it got there, unless you also log every event yourself. Time travel and audit are things you build.
  • The decision is a promise result. The model's answer flows into onDone and is gone. To replay without the model, you would store its outputs and inject them on replay.
  • The offer is hand-written. The options list repeats the guards. Vertep computes the offer from the guards, so the two cannot drift apart.
  • The host is yours. Where actors live, which of two processes owns one, and how a timer survives a deploy are your service's job.

XState follows SCXML's semantics closely and has tested itself against parts of the W3C suite, but its machines are JavaScript objects, not SCXML documents. Vertep reads SCXML directly and runs the full W3C conformance suite in CI. You can carry a chart from one to the other with the mapping at the end of this article.

The same desk in Akka

Akka, and Apache Pekko, its Apache-licensed fork, is the classic actor toolkit on the JVM. It has mailboxes, supervision, location transparency, Cluster Sharding for millions of entities, and Akka Persistence for event sourcing. In Akka Typed a state machine is usually written as event-sourced behaviour: commands come in, a command handler decides which events to persist, and an event handler folds them into the state.

sealed trait Command
final case class Request(amount: BigDecimal) extends Command
final case class Decide(choice: String, rationale: String) extends Command

sealed trait Event
final case class Requested(amount: BigDecimal) extends Event
final case class Decided(choice: String, rationale: String) extends Event

sealed trait State
case object Idle extends State
final case class Review(amount: BigDecimal) extends State
final case class Manager(amount: BigDecimal) extends State
final case class Done(outcome: String) extends State

def refund(id: String): Behavior[Command] =
  EventSourcedBehavior[Command, Event, State](
    persistenceId = PersistenceId.ofUniqueId(id),
    emptyState = Idle,
    commandHandler = (state, cmd) => (state, cmd) match {
      case (Idle, Request(a))                                   => Effect.persist(Requested(a))
      case (Review(a), Decide("approve", r)) if a <= 100        => Effect.persist(Decided("approve", r))
      case (Review(a), Decide("escalate", r)) if a > 100        => Effect.persist(Decided("escalate", r))
      case (Manager(_), Decide("approve", r))                   => Effect.persist(Decided("approve", r))
      case (Review(_) | Manager(_), Decide("reject", r))        => Effect.persist(Decided("reject", r))
      case _                                                    => Effect.unhandled
    },
    eventHandler = (state, evt) => (state, evt) match {
      case (Idle, Requested(a))                => Review(a)
      case (Review(a), Decided("escalate", _)) => Manager(a)
      case (_, Decided(outcome, _))            => Done(outcome)
      case (s, _)                              => s
    })
// something else asks the model and sends Decide to this entity

This is a sound design with a long production record. Event sourcing gives you recovery by replay, and Cluster Sharding gives you one live entity per id across a cluster. Compared with the chart:

  • The transition table is code, written twice. Once in the command handler, which decides what is allowed, and once in the event handler, which decides where it leads. Nested states, parallel regions and history are patterns you write by hand. There is no diagram to check them against.
  • You choose what to persist. That is flexible, and it means the record holds the domain events you thought of. A message that was refused, or a timer that fired into a state that ignored it, leaves no trace unless you add one.
  • Timers are not persisted. Behaviors.withTimers schedules in memory. A timeout that must survive a restart needs its own design.
  • The model sits outside. Akka has no notion of an offer. Whatever calls the model must know which choices are legal, and the entity must check again.

The same desk in Orleans

Microsoft Orleans introduced the virtual actor. A grain exists for every key, is activated on first call, and is deactivated when idle. The runtime guarantees one activation per key in the cluster. It has run large services, the Halo game backends among them, and it is a natural choice on .NET. Orleans offers plain persisted state, and JournaledGrain for event sourcing:

public interface IRefundGrain : IGrainWithStringKey
{
    Task Request(decimal amount);
    Task Decide(string choice, string rationale);
}

[GenerateSerializer] public record Requested([property: Id(0)] decimal Amount);
[GenerateSerializer] public record Decided([property: Id(0)] string Choice, [property: Id(1)] string Rationale);

public class RefundState
{
    public string Stage { get; set; } = "idle";
    public decimal Amount { get; set; }
    public void Apply(Requested e) { Stage = "review"; Amount = e.Amount; }
    public void Apply(Decided e) => Stage = e.Choice switch
    {
        "escalate" => "manager",
        "approve" => "approved",
        _ => "rejected",
    };
}

[LogConsistencyProvider(ProviderName = "LogStorage")]
public class RefundGrain : JournaledGrain<RefundState, object>, IRefundGrain
{
    public async Task Request(decimal amount)
    {
        if (State.Stage != "idle") throw new InvalidOperationException(State.Stage);
        RaiseEvent(new Requested(amount));
        await ConfirmEvents();
    }

    public async Task Decide(string choice, string rationale)
    {
        var allowed = State.Stage switch
        {
            "review" => State.Amount <= 100 ? new[] { "approve", "reject" } : new[] { "reject", "escalate" },
            "manager" => new[] { "approve", "reject" },
            _ => Array.Empty<string>(),
        };
        if (!allowed.Contains(choice)) throw new InvalidOperationException($"{choice} in {State.Stage}");
        RaiseEvent(new Decided(choice, rationale));
        await ConfirmEvents();
    }
}

Vertep borrows the virtual actor from Orleans, and a durable timer works much like an Orleans reminder. Orleans timers, by contrast, live only as long as the activation. The differences are the same as with Akka. The states are strings or classes you manage, the allowed moves are a switch you keep in step with the transitions, and the event log holds what you raise. Orleans scales very well. What it leaves to you is the shape of the behaviour.

When to choose which

Here is the honest version.

  • Choose XState for behaviour that lives in a user interface or a single service, where losing the history on a crash costs nothing and its tooling and community matter. Many apps should stop here.
  • Choose Akka or Pekko when you are on the JVM and need millions of live entities, streams and supervision, with a decade of operational knowledge behind you. The same goes for Orleans on .NET. If your hard problem is scale, they have solved it at sizes Vertep has not been tested at.
  • Choose Vertep when the hard problem is accountability. That means processes that wait for days, decisions made by models or people under rules that must hold, and a need to show later what happened and why, and to replay it. The chart bounds what any decider can do. The journal is written before the action. The record replays without the model. Regulated decisions, claims, approvals and agent workflows are the cases it was built for.

You can also mix them. A Vertep actor can sit behind an Akka or Orleans front end. An XState machine in the browser can drive the user interface for a Vertep actor on the server. And @vertep/web can run the same chart in the page when you want the journal there too.

Moving a chart across

If you have an XState machine, most of it maps one to one:

XState 5Vertep (SCXML)
states, initial<state>, initial="…"
type: "parallel", type: "history", type: "final"<parallel>, <history>, <final>
on: { ev: { target, guard } }<transition event="ev" cond="…" target="…"/>
alwaysA transition with no event
entry, exit<onentry>, <onexit>
context, assign<datamodel>, <assign> (CEL or ECMAScript)
after: { 900000: "expired" }<send event="timeout" delay="900s"/> on entry, plus a transition on it
raise, sendTo<raise>, <send target="…">
invoke of a promise that choosesA decide state: vt:decide and vt:candidates
invoke of a child machine<invoke> of a child chart

From Akka or Orleans, the move is the other way round. Draw the states your handlers imply, which is usually a revealing exercise. Turn each match arm or switch case into a transition with its guard, and let the event handler disappear, because step is the event handler. The entity id or grain key becomes the virtual actor's key. Reminders become delayed sends.

Try it on one process this week

  1. Pick one process that waits: an approval, a refund, an onboarding, a claim.
  2. Draw it. Write it as SCXML or typed YAML, and run vt validate and vt typecheck until both are quiet.
  3. Find every place where someone or something chooses. Make each one a decide state, and let the guards say what is allowed.
  4. Run it on a node with a virtual clock in a test. Send the events of a real case, drop the node, open the store again, and check that the state survived.
  5. Bind a scripted decider in tests and a model or an inbox in production. Then replay a production journal in CI with no decider at all.
  6. Check the stability tier of each part you depend on before you depend on it.

The docs have the full API. The examples are the programs quoted here, and the first article explains why the step function is pure.

Write down what may happen. Record what did. Then any machine, a year later, can tell you why.
