A reason that is not a story

Rules as a decider whose rationale is a derivation

Ask a language model why it approved a loan and it will give you a fluent answer. Ask a rule, and it gives you a list: these three facts about this case, and this clause. The first is a story the system tells about itself. The second is something you can check.

Two kinds of reason

A decider in Vertep chooses among the moves a chart offers: a language model, a person, or a program. Whatever it says about why is recorded, but the record treats the two cases differently. A model's rationale is its own account, kept and labelled as an unverified claim: the system stored what the model said and makes no promise that it is the cause. A rule's rationale is a derivation: the statements about the case that made the conclusion follow, listed by the rule itself, each of them a fact in the same file as the journal.

That difference is the point of this article. It is not that rules are smarter than models. It is that a rule's reason can be re-run.

A policy as a program

The credit example has a policy: approve if the debt-to-income ratio is at most 43% and the amount at most 50 000, and the chart actually offered approve. In Vertep that is a short program in ELPI, a λProlog, stored as a node in the same tiramemsu file as the journal it decides for:

tm.conclude (triple C (iri "urn:vt:decision") (iri "urn:vt:event:approve")) [X, Eo, Ed, Ea] :-
  tm.triple (iri "urn:vt:ctx") (iri "urn:vt:deciding") C X,
  tm.triple C (iri "urn:vt:offered") (iri "urn:vt:event:approve") Eo,
  tm.triple C (iri "urn:vt:ctx:dti") (num D) Ed, D =< 43,
  tm.triple C (iri "urn:vt:ctx:amount") (num A) Ea, A =< 50000.

Before the rule runs, the shell writes the offer and the plain fields of the case as statements, plus one that names the decision being made. The rule starts from that statement, finds the offered event, reads the two numbers, compares them, and concludes. The list in square brackets, [X, Eo, Ed, Ea], is the part that matters: the statements the conclusion rests on. The engine checks that every one of them was actually read during the run, so a rule cannot cite a fact it never looked at.

What the record shows

The credit example in the crate vertep-rules decides three applications and prints what the record says. Nothing below is written by hand:

deciding three applications by rule:
  1001  amount 20000, ratio 31%, offered ["approve", "decline", "refer"]
       derivation: approve from 4 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)
  1002  amount 80000, ratio 38%, offered ["decline", "refer"]
       derivation: refer from 3 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)
  1003  amount 45000, ratio 40%, offered ["approve", "refer"]
       derivation: approve from 4 statements by urn:vt:program:loan-policy (closure 73be31fe8c49)

the bundle of the first decision, verified with no shard:
  2403 bytes; urn:vt:decision:1001 concluded approve from 4 statements: verified

the next policy (ceiling 30 000) tried on the recorded decisions:
  2 unchanged, 1 differ
  urn:vt:decision:1003: approve -> refer

Loan 1002 asked for 80 000 against a ceiling of 50 000, and was offered only decline and refer. The rule concluded refer from three statements: the decision it was making, the fact that refer was offered, and the amount. That is the whole explanation, and each line of it is a statement an auditor can open.

The line also names a closure digest, 73be31fe8c49. A decision does not say a policy, it says this text of the policy, hashed, together with the engine version and the step budget it ran under. Edit the policy tomorrow and yesterday's decisions still point at yesterday's text, which the file keeps: a program is edited by superseding it, never overwritten.

Without the shard

The third block of the output is the one regulators care about. Take the first decision and export a bundle: the derivation, the program, and the supporting statements. The bundle is a plain JSON file of about 2.4 kilobytes. A fresh process, with no shard, no model and no network, loads the program, asserts the statements, runs the rule, and checks that it concludes the same event from the same statements. If someone edits the program text in the bundle, the digest no longer matches and verification fails. If they edit a statement, the rule no longer concludes the event, and it fails differently.

There is a limit worth stating, because it is a real one. A bundle carries only the statements the conclusion rests on. For a rule that only reads facts, that is enough. For a rule that reasons about what is absent, negation over facts outside the support, the offline run may not conclude what the live one did. The design notes say so, and the profile checks in the next article are how you keep rules on the right side of it.

What would the new rules have done?

The last block asks the question every policy change raises: if we had had the next version of the policy, which of our decisions would differ? counterfactual takes the recorded decisions and a program text, runs the program against the store as it was at each decision's transaction, and reports where the answer changes. With the ceiling dropped to 30 000, loan 1003 (45 000) would have been referred instead of approved, and the other two stand. Nothing is written: the journal and the live program are untouched, and the report can be handed to whoever must sign off on the change.

When there is no answer

A rule can fail to apply, and the decider says so. If nothing concludes, the answer is a refusal with the reason no-applicable-rule, never a default; a chart that wants a default declares a fallback decider. If the program concludes an event that was not offered, that is a refusal too (not-offered). If it runs out of steps, it is a refusal with the budget in the reason. A program may also refuse on purpose by concluding refuse. Evaluation is bounded by steps, never by a clock, so a replay uses the same budget as the original.

Why this and not a better prompt

A prompt can be asked to explain itself, and the explanation will be plausible. What it cannot be is re-run: the same model next month is a different function. A rule over recorded facts is the same function until its text changes, and the text is part of the record. That is the line this project keeps drawing between a story about a decision and the process that made it, and rules are the decider that sits on the right side of it. They are not always the right decider. A case that needs judgement belongs to a model or a person, and the chart is what keeps either from stepping outside the moves the policy allows.

The Rules page in the docs has the whole surface, and the next pages go through writing rules, operating them and checking them. The native engine library behind all of this is large and exists for macOS and Linux only, so rules are an optional feature: the browser and Python packages do not contain them.
