An agent that may not rewrite its own rules

Proposing, shadowing and promoting rules, with a gate

Rules that agents can write are rules agents can weaken. The question is not whether to let a model draft policy, since a model that has read a year of refused cases is a good drafter, but what stands between its draft and the live system. This is the answer Vertep gives.

Four ideas

The design rests on four ideas, in order of importance.

  1. A proposal is inert. It is stored as a program node of its own, under a name derived from its text, with its author and the grant it used. No decider reads it and no enforcement runs it. Until a person moves it, it changes nothing.
  2. The gate fails with something an agent can repair. Not a message: a stable code, the clause at fault and the reason.
  3. Evidence comes before effect. A proposal runs in shadow beside the live program on recorded cases and records where it would have decided differently, without deciding anything.
  4. An actor never changes the rules that govern it. Not by permission: by construction.

The gate

A proposal passes six checks, in this order, and the first failure stops it:

CodeWhat was checked
self-governanceThe program's scope, the actors it would govern, does not include the proposer.
capabilityThe proposing identity may propose, by a function the host supplies.
type-errorEvery event the program concludes is one the chart declares (or refuse).
profileThe program is inside the rules profile: no cut, no findall, no effects, negation stratified.
no-cases / trial-failedA trial run on recorded decisions, under a step budget, succeeds. With no cases the proposal is refused unless a promote-grant holder waives it.
existing-dataFor a program with constraints, the data already in the shard does not violate them.

The agent reaches the gate through a tool, vt:tool/rules/propose, taking { text, source } and returning { proposal }. The caller's identity is fixed when the tool is built; it is never an argument, so an agent cannot claim to be someone else. A refusal comes back as JSON, for example:

{"code": "type-error", "clause": "tm.conclude (triple C (iri \"urn:vt:decision\") (iri \"urn:vt:event:reject\")) ...", "reason": "the chart declares no event `reject`"}

An agent reads that, edits the clause, and proposes again. The test suite runs exactly this exchange: a first attempt concluding an undeclared event is refused with type-error, a second with the event corrected is stored.

Shadow, then stages

Shadow evaluation takes the recorded decisions, runs the proposal over each, and writes a record of every case where its conclusion differs from the recorded one. It can sample every nth case when the history is long. It never decides anything and never appends.

Promotion then has three stages, each a separate act that is itself recorded (who, which stage, which scope, the digest of the program):

  1. Shadow. The proposal is approved for shadow evaluation.
  2. Scoped. It is live for a named scope. A decider bound to that scope runs the proposal; every other decider still runs the live program.
  3. Live. It replaces the live program for everyone, by superseding it, so the old text stays readable.

A stage cannot be skipped: asking for live from proposed is refused with skipped-step and names the step that is missing. Promotion needs a promote grant, which a host would not give to the proposing agent.

The rule about rules

Everything above could be undone if an agent were allowed to propose, edit or promote a rule that governs itself. So that is refused structurally. Every proposal declares the actors it would govern; if the proposer, or the identity promoting it, is one of those actors, the answer is self-governance, whatever grants it holds. The check is not a permission an administrator could widen by accident. A different reviewer, holding the promote grant and not governed by the rule, can promote it, and that is the only way a rule reaches the actors it binds.

What is left to the host

Two things are deliberately not decided by the library. The capability check is a function the host supplies; the command line reads it from a small JSON file, and wiring federation grant credentials into it is an integration, not part of this change. And a scope is a setting of a decider, not a value of a request. The docs page on authoring has the commands and the codes.

The general principle is older than any of this: a system that can be changed by what it governs has no governor. The gate is a way of making that sentence true in code.
